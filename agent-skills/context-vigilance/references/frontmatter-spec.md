# Frontmatter Spec for `context-v/` Documents

**Contents:** Exact vs. judgment · Property names: always `snake_case` · Canonical example · Baseline fields · `lede` and `summary` · Dates · Optional fields · Identity fields: `site_uuid` and `hex_code` · `publish` and sensitive content · Authors and `augmented_with` · Tags · Date format and title quoting · Validation philosophy and the plugin hook · Directed normalization sweeps

> **In practice, frontmatter is uneven.** Some files carry status, supersedes, related, aliases; others only `title` and `date_created`. Both are fine. This is the baseline for *new* files, not a checklist to fail old ones against. Be generous reading; be thoughtful writing.

Markdown files under `context-v/` start with YAML frontmatter between `---` lines.

## Exact vs. judgment

- **Exact** (one right answer): key names in `snake_case`; dates as `YYYY-MM-DD`; version as four-part `e.M.m.p`; `site_uuid` as lowercase UUID v4; `hex_code` as 6 chars of `[a-z0-9]`; IDs generated by a command, never typed; `site_uuid`/`hex_code` never changed once set.
- **Shaped** (default pattern, deviate with a reason): Train-Case tags and status values, the `lede` length budget, `authors` humans-only, which optional fields you use.
- **Open** (judgment): `publish`, what to genericize, when to split a doc, what goes in `summary`.

## Property names: always `snake_case`

**All frontmatter keys are `snake_case`** (exact).

- Yes: `date_created`, `augmented_with`, `at_semantic_version`, `superseded_by`, `implements_spec`
- No: `dateCreated`, `augmented-with`, `SemanticVersion`, `supersededBy`

One consistent case means every consumer (static-site content collections, scripts, search indexes) can read keys without guessing. If your `context-v/` is opened in Obsidian, it matters more: Obsidian's property panel and indexing handle `snake_case` cleanly, while camelCase and kebab-case keys behave inconsistently there.

The rule covers **keys only.** Values: `tags` and `status` are Train-Case (`Markdown-Rendering`, `Signed-Off`); `authors` and `augmented_with` are free-form strings; dates are `YYYY-MM-DD`.

When you find an existing non-`snake_case` key, **surface it rather than silently renaming it.** Build tooling may read the field by its current name.

## Canonical example

```yaml
---
title: "Maintain an Extended Markdown Render Pipeline"
lede: "Why our markdown pipeline is the asset, and where it's heading next."
date_created: 2026-03-30
date_modified: 2026-05-03
authors:
  - Jane Doe
augmented_with:
  - Claude Code on Claude Opus 5.5
at_semantic_version: 0.1.2.0
site_uuid: 3f2b8c1e-9a4d-4e7f-b6c2-1d5e8f0a7b93
hex_code: k7m2q9
tags:
  - Markdown
  - Rendering
---
```

(The ID values above are illustrations. Generate your own; see *Identity fields*.)

## Baseline fields

Recommended on new files.

| Field | Type | Notes |
|---|---|---|
| `title` | string | Human-readable, Title Case. Quote it if it contains a colon. |
| `lede` *(or `description`)* | string | The one line under the title on a card, list view, or social preview. **140 characters max, target 90–130.** See below. Optional on any doc-type. |
| `publish` | boolean | Whether the doc should render on a public site. A judgment made by *reading*; see *`publish` and sensitive content*. Never flip an existing value. |
| `date_created` | YYYY-MM-DD | **Filesystem-ish.** When the file appeared. Set once; never overwrite an existing value with `stat`. Legacy spelling `created:` renames to this, value verbatim. |
| `date_modified` | YYYY-MM-DD | **Filesystem-ish.** Update on every meaningful edit. Read it before editing; never stamp today as a side effect of an automated pass. |
| `date_authored_initial_draft` | YYYY-MM-DD | **Editorial.** When the content was first real and coherent, not when an empty file was created. Set once. Legacy spelling `date:` renames to this. |
| `date_authored_current_draft` | YYYY-MM-DD | **Editorial.** When the doc last got a *substantive* revision. Never earlier than `initial_draft`. Moves together with `at_semantic_version`. |
| `authors` | list of strings | **Humans only.** Always a list. |
| `augmented_with` | list of strings | AI tools used, as `<tool> on <model and version>`. |
| `at_semantic_version` | string `e.M.m.p` | Four-part; new docs start at `0.0.0.1`. `semantic_version` is a permanently-accepted alias: write `at_`, read either (`at_semantic_version ?? semantic_version`), never rewrite a file just to change the name. See `versioning.md`. |
| `site_uuid` | lowercase UUID v4 | Stable identity. Generated once at creation. See *Identity fields*. |
| `hex_code` | 6 chars `[a-z0-9]` | Citation ID. Generated once at creation. See *Identity fields*. |
| `tags` | list of strings | Train-Case. At least one. |

If an existing file lacks baseline fields, **don't add them during unrelated edits**; surface the gap. Frontmatter changes are a separate concern from content changes (unless the user directs a sweep; see the last section).

## `lede` and `summary`

**`lede`** exists because `title` says *what a thing is* and a `description` is usually too long and too dull for a card. The lede says *why you'd care*, at a glance.

- **Hard budget: 140 characters, target 90–130, two rendered lines.** Social unfurls truncate around 200 characters and list cards wrap sooner, so a longer lede clips mid-sentence exactly where it's meant to work. Vague guidance like "a few sentences" doesn't hold: a batch of ledes written to that wording once averaged ~370 characters and all had to be rewritten.
- **Write one clause that lands**, not a sentence with a trailing subordinate clause.
- **Never trade specificity for brevity.** A short generic lede ("A profile of a vector database") is worse than none.
- When the lede wants to grow, that material belongs in a `## Why Care?` section in the body. If a doc genuinely can't be hooked in 140 characters, say so rather than papering over it.
- `lede` is preferred over `description` because the word signals the job; both are accepted.

**`summary`** is the agent-facing counterpart. It answers what an agent asks before opening the file: *what is this for, where does it sit in the workflow, what consumes it, what should I do with it* ("read this before touching X," "the spec it points at is the authority"). Nothing renders it in a card, so it can be as long as orientation needs. Most valuable on docs agents must triage: specs, blueprints, handoffs, issues.

| | `lede` | `summary` |
|---|---|---|
| Audience | humans, pre-click | agents, and humans orienting mid-workflow |
| Voice | newsroom hook | plain, declarative |
| Consumed by | list views, preview cards, social unfurls | agent retrieval, indexing, triage |
| Length | 140 chars max | a few sentences, freely longer |

Keep them separate: stuffing workflow context into `lede` degrades the card it feeds.

**`summary` may already be claimed.** Some repos historically used `summary` as a spelling of `lede`. On a file with `summary` and no `lede`, the value is almost certainly a legacy lede. A renderer doing `lede ?? summary` will then show agent prose in a human slot; the fix is to write a real `lede`. Migrating a legacy `summary` is a content edit, not a normalization.

## Dates

### Filesystem dates lie, which is why the editorial pair exists

"When did this last really change?" is the question `context-v/` has to answer, and the filesystem can't:

- **`date_modified` overstates recency.** Some editors and plugins (Obsidian templaters, for one) bump it when a file is merely opened.
- **`date_created` can overstate age-of-origin.** Copies, clones, and machine restores reset birthtime. Where frontmatter records an *earlier* `date_created` than `stat` reports, **the frontmatter is the better record.** Never overwrite it.
- A missing `date_created` should come from `date_authored_initial_draft` before filesystem birthtime: a document can't be created after its own first draft.

**Source precedence when a date must be derived** (use the first that resolves; `stat` is last):

1. An existing frontmatter date on the same file.
2. A date in the filename (`2025-11-26_03.md` → `2025-11-26`).
3. A date stated in the body (release notes often name their ship date).
4. Git's first-commit date: `git log --diff-filter=A --follow --format=%ad --date=short -- <file> | tail -1`. The strongest derived source.
5. Filesystem `stat`, treated as suspect.

The tell that `stat` is wrong: a uniform birthtime across files of obviously different ages (from a bulk copy or restore). When you see it, drop to git.

### Work dates vs. document dates

The other dates describe the **document**. `date_work_started` / `date_work_completed` describe the **work it describes**. For plans these come apart hard:

```yaml
date_authored_initial_draft: 2026-04-02   # plan written
date_authored_current_draft: 2026-04-28   # revised as scope moved
date_work_started: 2026-04-08             # implementation began
date_work_completed: 2026-06-11           # shipped
```

None is derivable from another. Timelines keyed on authorship show when someone typed, not when anything happened; questions like "how long did this take" or "which plans were never worked" need the work axis.

- **Optional, independently.** `date_work_completed` alone is useful. Write what's known.
- `date_work_completed` must not precede `date_work_started`.
- **Never derive them from the filesystem, and don't backfill from memory.** An absent field is honest; a guessed one corrupts the timeline.
- Usually set `date_work_completed` in the same edit that moves `status` to `Shipped`, alongside `date_first_published` (which records when the *result* went out; they differ when work finishes but is held).

## Optional fields

Add as needed; don't invent fields without precedent in the project.

| Field | Purpose |
|---|---|
| `summary` | Agent-facing orientation. See above. |
| `status` | Train-Case display string (`Draft`, `In-Review`, `Signed-Off`, `Implementing`, `Shipped`, `Partially-Shipped`, `Deferred`, `Stale`, `Superseded`, `Archived`). **Not a machine enum**: don't switch on it in code. Some values require companion fields; see `status-discipline.md`. |
| `date_authored_final_draft` | `YYYY-MM-DD`, or **present-but-empty** meaning "not final yet." Don't delete the empty key; its presence signals finality is tracked. |
| `date_first_published` | `YYYY-MM-DD`. Set when `status` first becomes `Shipped` or `Partially-Shipped`. Never updated after. |
| `date_work_started` / `date_work_completed` | See *Work dates*. |
| `date_last_updated` | Any touch, substantive or not (contrast `date_authored_current_draft`). |
| `post_ship_note` | Multiline. Things learned after `Shipped`. |
| `deferral_note` | Multiline. Required with `status: Deferred`: reason and expected unblocker. |
| `supersedes` / `superseded_by` | Wikilink or filename of the replaced / replacing doc. |
| `related` | List of `[[wikilinks]]`. |
| `aliases` | Alternate titles for wikilink resolution (Obsidian reads this). |

## Identity fields: `site_uuid` and `hex_code`

Two stable identifiers, cheap to generate and **write-once** (exact). **Write them on every new file.** Retrofitting identity onto hundreds of documents later is far more expensive than minting it at creation.

| Field | Shape | Set |
|---|---|---|
| `site_uuid` | UUID v4, lowercase, hyphenated | once, at creation; never regenerated |
| `hex_code` | 6 chars, `[a-z0-9]` | once, at creation; never regenerated |

### Why the filename is not enough

A bare `[[Filename]]` resolves by walking the tree, and it's ambiguous as soon as a document is copied: rolled up into a parent repo, mirrored into a site's content folder, vendored elsewhere. The same file can exist in half a dozen places. **`site_uuid` is what distinguishes "six copies of one document" from "six different documents"** when the filenames match. So the identifier **travels with the document into every copy**; copies sharing a `site_uuid` is correct, not a duplicate to clean up.

It also survives renames (docs get retitled as scope sharpens), disambiguates same-named docs across repos, and gives retrieval and sync tools a stable key that survives re-ingest, moves, and renames.

### Why `site_uuid` and not `uuid`

Databases issue their own `uuid` primary keys. A document synced into one would carry two meanings under one key name. `site_uuid` names the identity owned by the *source* (the repo, wherever it renders) and leaves `uuid` free for whatever store the document lands in; sync layers map `site_uuid` → their own key without collision.

### `hex_code`: the document's own citation ID

`hex_code` lets documents cite each other with stable footnote markers. Inline markers, definitions in a `## References` section:

```markdown
The sweep found the standard was being restated inconsistently.[^a4f2c1]

## References

[^a4f2c1]: [[Frontmatter-Normalization-Plan]]
```

This is standard Markdown footnote syntax (Obsidian renders it with hover previews). **Reuse the cited document's `hex_code`** so the same citation reads identically everywhere. **Never sequential `[^1]`**: sequential markers collide the moment a paragraph is copied between documents.

### Generating them: a command, never the model

**An agent must shell out for these. It must never type an identifier from its own head** (exact). A model "inventing" a UUID emits something UUID-*shaped*, drawn from training-data frequency: biased, repetition-prone, not unique. We've seen model-typed `site_uuid` values containing characters that aren't hex at all (`1n870f09-…`, `…-396h-4rb4-…`). They aren't valid UUIDs and fail any strict parser.

```bash
# site_uuid (any of these)
uuidgen | tr 'A-Z' 'a-z'
python3 -c "import uuid; print(uuid.uuid4())"
node -e "console.log(crypto.randomUUID())"

# hex_code: 6 chars of [a-z0-9]
LC_ALL=C tr -dc 'a-z0-9' </dev/urandom | head -c6; echo
python3 -c "import secrets,string; a=string.ascii_lowercase+string.digits; print(''.join(secrets.choice(a) for _ in range(6)))"
```

### The charset matters more than the name suggests

**`hex_code` is a misnomer: the charset is `[a-z0-9]` (base36), not `[0-9a-f]`.** Keep the name; don't narrow the charset. Chance of at least one collision (birthday bound):

| Documents | 6 chars true hex (16⁶ ≈ 16.8M) | 6 chars `[a-z0-9]` (36⁶ ≈ 2.18B) |
|---|---|---|
| 1,000 | 2.9% | 0.02% |
| 3,000 | **23.5%** | 0.2% |
| 10,000 | **94.9%** | 2.3% |
| 25,000 | ~100% | 13.4% |

So `openssl rand -hex 3` is the **wrong** generator despite being the obvious one. Use the `tr -dc 'a-z0-9'` form.

### Check before you commit

The repo is the registry. From the repo root (or the parent that holds related repos):

```bash
grep -rl "<the-new-code>" --include='*.md' .
```

No output means it's free; regenerate on a hit. Worth doing for `hex_code`; unnecessary for `site_uuid`.

### Retrofitting is a directed pass, not a side effect

Adding these to existing files can't break a render, but it isn't free: a naive pass over every file would give *different* `site_uuid`s to copies of the same document, permanently breaking the dedup property. **Edit originals, never copies.** Until the user directs a retrofit, write IDs on new files and leave existing ones alone.

## `publish` and sensitive content

Most `context-v/` work is fine to publish. The goal isn't secrecy; it's a light habit: **write generically about specifics that aren't yours to share.**

### What `publish` does (and doesn't)

`publish` is a **website gate**: it decides whether a doc renders on a public site. It is not necessarily honored by search, retrieval, or indexing tools; many deliberately read unpublished docs, since internal docs are often the most useful to retrieve. **Don't reach for `publish: false` as a confidentiality control** without checking what your tools actually honor (some use a separate `private: true`). A confidentiality problem is solved by genericizing the sentence, excluding the file from the tools that matter, or, for a live credential, rotating it, since the value is in git history regardless.

Judge `publish` by **reading** the doc: `true` if a reader would get real value; `false` for a stub, a title with nothing under it, a body of `<!-- developing -->` placeholders, or raw session-transcript text that isn't reader-ready. A stale "Stub" banner over a developed body is `true`; a polished title over twelve empty sections is `false`. Word counts get both backwards. **Borderline resolves to `false`:** unpublished-by-default is recoverable; publishing a client's scorecard is not. **If the key exists, never flip it**, especially not `false` → `true`.

Check the repo's own habit first; there's no safe global default:

```bash
grep -rh '^publish:' --include='*.md' context-v/ | sort | uniq -c
```

A repo running 47 `false` to 5 `true` has made a decision; treat a `true` there as the exception that needs justifying.

### Genericize first; `publish: false` is the fallback

| Instead of | Write |
|---|---|
| "AcmeCo's site was built before the carve-out" | "the first client site was built before the carve-out" |
| "Jane Chen, formerly of Acme, 18% IRR" | "a partner with a prior fund track record" |
| "the round is mostly committed at $12M" | *(cut it; it adds nothing to an engineering doc)* |
| a client's 12-dimension rubric reproduced verbatim | "the client's scoring framework has ~12 weighted dimensions" |

**The document's job comes first.** Ask in order:

1. **Does it do its job as well genericized?** Usually yes for engineering docs. Genericize and keep `publish: true`.
2. **Is it materially better *with* the specifics?** Then keep them and set `publish: false`. A plan naming the real client and deliverable is easier for the next agent to act on. That's not a demotion; plenty of `context-v/` is legitimately internal.

Never water down a useful internal doc for a publication that was never going to happen.

**Wants genericizing:** PII (named individuals with biography, performance, or judgment attached); a client's trade secrets (proprietary frameworks, rubrics, brand IP); confidential deal terms on identifiable companies; reproductions of third-party confidential documents; client names where naming adds nothing.

**Fine, don't over-screen:** env-var *names* (`SESSION_SECRET`; values obviously aren't); architecture, schemas, file layouts, route tables; the fact that client work happened, described generically; your own conventions and post-mortems; illustrative placeholder data.

The docs that most often need a second look are the ones *about* handling confidential material (private-data patterns, auth setups, data rooms): they tend to quote the very paths and names they exist to protect.

### Credentials that don't look like credentials

"Never paste a live credential" is the rule. What actually leaks doesn't look like a value:

| Looks like | Actually is |
|---|---|
| An **access key ID** (`AKIA…`, S3-compatible key IDs) | Half a key pair, and it names the account to attack. |
| A **salt** committed next to the hash it salts | Hands over an offline cracking job. |
| A **password/passcode hash** with a human-chosen passcode | Crackable when the salt is adjacent. |
| An **account ID inside an endpoint URL** | Not secret, but pins the account; redact for hygiene, don't panic-rotate (account IDs can't be rotated anyway). |
| A **token's ID** vs. its value | Some providers derive the secret from the token, so ID and secret are two faces of one thing. |

The test: **would this value, plus one more thing an attacker might get, grant access?** If yes, treat it as a credential.

### Write hot, redact at the commit boundary

Credential leaks come from docs written *during* the work, with real values pasted in because you're using them. Forbidding that makes the notes worse, so the rule is a boundary:

1. **While working:** paste what you need. The working tree isn't the risk.
2. **Before `git add`:** sweep the staged diff:
   ```bash
   git diff --cached -U0 | grep -nE '\b[0-9a-f]{32,64}\b|(KEY|TOKEN|SECRET|SALT|HASH|PASSCODE)[A-Z_]*\s*[:=]'
   ```
3. **Replace with the retrieval path, not a blank:** `<CLOUD_ACCOUNT_ID>` or "in the secrets manager as `R2_ACCESS_KEY_ID`" keeps the doc useful.
4. **Already pushed? Rotate.** Redacting the working tree does nothing about history.

**One document can be several files.** If `context-v/` is copied anywhere (a parent repo roll-up, a site's content folder, a search-index mirror, a vendored copy), redacting the source isn't enough. Grep every copy for the value; regenerating mirrors doesn't remove a stale copy that's already committed.

## Authors and `augmented_with`

**`authors` is for humans only** (shaped). Even when an agent wrote most of the prose, the human directing the work is the author. Use full preferred names, always as a list; order by contribution or alphabetically.

**`augmented_with`** records AI tooling, one `<tool> on <model and version>` entry per pair: `Claude Code on Claude Opus 5.5`, `Codex on GPT-5`, `Cursor on GPT-5`. Avoid generic strings (`"AI Assistant"`, `"ChatGPT"`). Include it whenever an agent contributed materially; honesty about augmentation matters more than credit allocation.

## Tags

- **Train-Case:** `Markdown-Rendering`, not `markdown-rendering`, `MarkdownRendering`, or `markdown_rendering`. (In Obsidian, hyphenated Train-Case is one tag; other separators behave inconsistently.)
- Single words are capitalized: `Spec`, `Markdown`. Singular over plural: `Spec`, not `Specs`.
- Reuse existing tags before inventing new ones:
  ```bash
  grep -rhA20 '^---' context-v/ | grep -E '^  - [A-Z]' | sort -u
  ```

## Date format and title quoting

Dates are always `YYYY-MM-DD` (exact): no timestamps, no timezones. If you need a timestamp, use a separate field (`last_run: 2026-05-03T14:32:00Z`).

Quote a title that contains a colon, starts with a number (`"2026 Plan"`), or contains YAML-special characters (`#`, `&`, `*`, `!`, `|`, `>`, `'`, `"`, `%`, `@`, `` ` ``). When in doubt, double-quote.

## Validation philosophy and the plugin hook

Beyond a small exact core, frontmatter is **not hard-validated**. Be lenient reading existing files; older files that predate a convention aren't bugs. If frontmatter is genuinely broken (malformed YAML, missing `title`), fix it as a `patch` bump. Don't auto-migrate names or styles unless asked. **Never delete a key you don't recognize**: different surfaces read different keys, and an unused key costs nothing. Not knowing a field is a reason to ask, not to remove it.

**The plugin hook.** The context-vigilance-kit plugin ships a hook that runs before writes to `context-v/**` (excluding `extra/`) and blocks only when: the YAML doesn't parse; `title` is missing; `date_created`/`date_modified` isn't `YYYY-MM-DD`, or modified is earlier than created; `site_uuid` isn't a lowercase UUID v4; `hex_code` isn't 6 chars of `[a-z0-9]`; or `site_uuid`/`hex_code` changed on an edit. New files need all five fields (`title`, `date_created`, `date_modified`, `site_uuid`, `hex_code`); older files are checked only for the fields they already have. Everything else in this spec stays judgment.

## Directed normalization sweeps

"Don't auto-migrate" governs **incidental** edits. When the user explicitly asks to bring a directory up to standard, these bind:

1. **Additive only.** Add missing keys; rename legacy spellings (`created:` → `date_created:`, `date:` → `date_authored_initial_draft:`) with values verbatim. Change nothing else.
2. **No YAML round-trips.** Serializing through a YAML library reorders hand-authored keys and collapses multi-line blocks. Edit lines in place; append new keys at the end of the block.
3. **Never touch the body.** The diff is frontmatter lines only.
4. **`publish` can't be mechanized.** It requires reading. An existing value is a decision; never flip it.
5. **Don't stamp `date_modified` with today.** Adding a key isn't a substantive edit, so it doesn't move `date_authored_current_draft` or bump the version either.
6. **Edit originals, never copies.** Roll-ups, mirrors, and vendored copies regenerate from source.
7. **Grep for consumers before a rename lands.** Renaming a key is easy; finding what *read* the old key is the work. A `date:` → `date_authored_initial_draft` rename once silently broke two ingest scripts that read `date`.
8. **Skill files are out of scope.** `SKILL.md`, its `references/`, and its README under `context-v/agent-skills/` follow the skill-authoring contract, not this spec: harnesses parse `name` and `description` to decide whether a skill loads. Don't count them in audits or reorder their keys.
